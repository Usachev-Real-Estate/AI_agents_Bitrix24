Проект живой и функционально богатый: детерминированные правила аудита, авто-переносы
сделок, рейтинг брокеров, локи полей, отчёты в чаты. Архитектура (collectors → analysts →
dispatcher на LangGraph) читаемая, есть docstrings и типизация.

Главный риск — **не техдолг, а последствия ошибок**: система автоматически переносит
сделки в «Общую базу», меняет поля в CRM и публично снижает рейтинг брокеров. При этом
сбои сбора данных проглатываются молча, и аудит доходит до конца на неполных данных.

## Критические находки

### C1. Сбой загрузки таймлайна молча превращается в нарушение и авто-перенос сделки

`src/tools.py:2760`, `src/tools.py:2800`, `src/tools.py:2866`, `src/tools.py:3036`

```python
except Exception:
    logger.debug("Timeline fetch failed for %s id=%s", entity_type, entity_id)
    return (entity_id, [])
```

Пустой таймлайн неотличим от «комментариев нет». Дальше по цепочке:

`check_seller_deal_violations` (`tools.py:1327`) → `seller_stage_stale` →
`process_deals_to_general_base` (`tools.py:688`) → `crm.item.update` — **сделка уезжает
в «Общую базу»**, брокер получает нарушение в чат отдела и минус в рейтинг.

Любая сетевая ошибка или троттлинг Bitrix (а запросов тысячи, см. P1) даёт ложные
обвинения и необратимую мутацию CRM. Логируется на уровне `DEBUG`, при `LOG_LEVEL=INFO`
не видно вообще.

**То же с `_build_rop_map` (`tools.py:975`) и `_build_broker_dept_map` (`tools.py:993`):**
при сбое возвращается пустая карта → комментарии РОПов перестают засчитываться → массовые
ложные нарушения по всем отделам сразу.

**Что сделать:**
1. Различать «данных нет» и «не удалось получить»: возвращать `None`/флаг `fetch_failed`.
2. Ввести run-level gate: если доля неудачных загрузок > N % — отменить мутации и отправку
   отчётов, уведомить админа.
3. Повысить уровень логирования до `WARNING` и считать метрику ошибок за прогон.
4. Ретраи с backoff на уровне отдельной сущности.

### C2. Мутации CRM выполняются до фильтров диспетчера

`src/graph.py:238` (buyers), `src/graph.py:295` (sellers) → `process_deals_to_general_base`

Аналитики переносят сделки **сразу**. Диспетчер (`graph.py:558`) только потом отсеивает:

* `_sanitize_violations` — правила вне политики (`graph.py:568`);
* уволенных сотрудников — `if uid in inactive_users: continue` (`graph.py:602`);
* отделы «Бэк-офис» и «Битрикс» (`graph.py:607`).

Итог: сделка сотрудника из исключённого отдела или уволенного брокера **переносится
в «Общую базу», но в отчёте не появляется**. Мутация без следа в отчётности.

**Что сделать:** перенести `process_deals_to_general_base` в диспетчер, после всех
фильтров, либо применять те же фильтры внутри аналитиков.

### C3. `DRY_RUN=true` не защищает БД — и портит рейтинг брокеров

`src/graph.py:954-988`

`save_audit_run`, `save_violations`, `upsert_brokers` вызываются **вне** проверки
`settings.dry_run`. Единственный барьер — `is_routine_audit_run` (`db.py:31`), который
разрешает запись, если прогон попал в окно 07:0x/14:0x UTC в будни.

Нарушения из БД напрямую питают рейтинг: `broker_rating.py:286` →
`get_violations_for_broker`, `broker_rating_collectors.py:291` →
`count_violations_on_date`. То есть **dry-run, случайно запущенный в окно cron,
публично снижает рейтинг живых брокеров**.

Наличие `purge_test_violations()` (`db.py:359`) показывает, что на эти грабли уже
наступали — но это лечение, а не профилактика.

**Что сделать:** при `dry_run=True` не писать ни в `audit_runs`, ни в `violations`,
ни в `brokers`.

### C4. Соединения SQLite никогда не закрываются

`src/db.py` — 38 вхождений `with get_connection() as conn`, **ноль** `conn.close()`.

`sqlite3.Connection.__exit__` делает commit/rollback, но **не закрывает** соединение.
Каждый вызов функции БД оставляет висящий handle и файловый дескриптор; в WAL-режиме
такие соединения удерживают read-lock и мешают чекпойнту WAL (файл `-wal` растёт).

Сейчас смягчается тем, что процессы короткоживущие (`docker run --rm`), но
`chat_poller` и длинные прогоны аудита выполняют десятки вызовов подряд.

**Что сделать:**
```python
from contextlib import closing
with closing(get_connection()) as conn, conn:
    ...
```
и заодно выставить `PRAGMA busy_timeout=10000` — 9 cron-задач пишут в одну базу.

## Производительность

### P1. N+1 запросов к Bitrix24 — узкое место всего аудита

`tools.py:2854` (лиды), `tools.py:3025` (сделки), `tools.py:3040` (активности):

```python
with ThreadPoolExecutor(max_workers=MAX_TIMELINE_WORKERS) as pool:
    futures = {pool.submit(_fetch_entity_timeline, lid, "lead"): lid for lid in lead_records}
```

**Один REST-вызов на каждую сущность.** Для 3 000 лидов + 2 000 сделок это ~5 000
вызовов `crm.timeline.comment.list` плюс ~2 000 `crm.activity.list` за прогон.
Bitrix24 ограничивает webhook ~2 req/s — при активном троттлинге прогон растягивается
на десятки минут, а каждая деградация превращается в C1.

`fast_bitrix24` умеет батчинг: `bx.call(method, [params1, params2, ...])` упаковывает
до 50 команд в один `batch`-запрос. Это даёт **сокращение числа HTTP-запросов ~в 50 раз**.

**Что сделать:** заменить пул потоков на батч-вызовы по 50 сущностей.

### P2. Дублирующая загрузка воронок

`graph.py:152` и `graph.py:171` вызывают `get_deals_by_funnel_with_timeline` для
`buyers_category_id` и `sellers_category_id`. При `BUYERS_CATEGORY_ID == SELLERS_CATEGORY_ID`
(оба поля имеют default `0`) весь тяжёлый сбор выполняется дважды. Кэша нет.

### P3. `_fetch_user_calls_for_audit(hours_ago=720)`

`tools.py:2877` — история звонков за **30 дней** на каждого ответственного, при том что
аудит идёт от `REPORT_SINCE`. Кэш по `assigned_id` есть, но объём данных избыточен.

## Корректность и логика

### L1. `send_chat_message_chunked` не режет длинные строки

`notify.py:120-145`: разбиение только по `\n`. Одна строка длиннее `chunk_size`
(4000 / 1800) уходит в чат целиком и обрезается Bitrix. Причина реальна: `reason`
нарушения склеивается из текста CRM + `GENERAL_BASE_MOVE_WARNING` (`tools.py:130`).

Константа `MESSAGE_MAX_LEN = 2000` (`notify.py:13`) объявлена и **не используется** —
при этом реальные chunk_size равны 4000 и 1800.

### L2. Мёртвая логика дедупликации прогонов

`graph.py:571-579`: `last_violation_count` инициализируется `-1` (`graph.py:1067`),
`report_sent` — `False`. Диспетчер в графе один и вызывается один раз за прогон,
состояние между запусками не сохраняется. Ветка «skipping unchanged» недостижима.

### L3. Даты без таймзоны трактуются как UTC

`tools.py:346` `_parse_datetime`: fallback `%Y-%m-%d` → `tzinfo=UTC`. Портал работает
в MSK (UTC+3), в конфиге даже есть `BUYER_COMMISSION_TIMEZONE=Europe/Moscow`.
Для date-only полей (`EXCLUSIVE_END_DATE_FIELD`, `REPORT_SINCE`) даёт смещение 3 часа —
на границах суток меняет вердикт правила.

### L4. Захардкоженные бизнес-значения в коде

* `graph.py:607` — `{"Бэк-офис", "Битрикс"}` строками в коде;
* `db.py:8` — `ROUTINE_AUDIT_SINCE_CUTOFF = "2026-06-01"`;
* `db.py:43-49` — окно cron `{7, 14}` UTC зашито; смена расписания в `crontab.txt`
  тихо ломает сохранение нарушений;
* `DEPT_CHAT_MAP` в `DEPLOY.md` документирован таблицей, но живёт в `.env`.

### L5. Избыточная защита от несуществующего случая

`broker_score.py:145` и `owner_tracker.py:321`:
```python
if str(settings.dry_run).lower() != "true" and settings.dry_run is not True:
```
`dry_run` — pydantic `bool`, достаточно `if not settings.dry_run`. Два разных стиля
проверки одного флага в одной кодовой базе — источник будущих расхождений.
