# LLM для обработки текста в карточке: что выбрать и как спрашивать

**Дата:** 2026-08-20 · **Статус:** рекомендация. Код не меняется.
Продолжает `SELLERS-COMMENT-QUALITY.md` — там показано, почему регулярками задача не решается.

---

## Короткий ответ

1. **Остаться на DeepSeek**, которая уже подключена. Второго провайдера не заводить.
2. **Спрашивать не «хорош ли комментарий», а «какие факты в нём есть».**
   Это важнее выбора модели.
3. **Сначала починить дисциплину вызова** (JSON-схема, `temperature=0`, кэш),
   потом обсуждать модель. Большая часть текущих проблем — не про модель.

## Часть 1. Главное: что спрашивать у модели

Есть два способа применить LLM к комментарию брокера, и они расходятся
принципиально.

### Оценочный (не надо)

> «Оцени, содержательный ли это комментарий» → `{"good": false}`

Что не так:
- **Спорится.** Вердикт модели о работе человека — предмет конфликта с отделом,
  причём конфликта, в котором РОП не сможет объяснить логику.
- **Не тестируется.** Нет объективной разметки «хороший/плохой» — значит нельзя
  измерить качество и нельзя заметить деградацию после смены версии модели.
- **Обходится.** Модель проще обмануть связной прозой, чем человека. Отдел
  быстро выучит стиль, который нравится модели, — и мы вернёмся к ритуалу,
  только более дорогому и более убедительному на вид.
- **Дрейфует.** Смена версии модели молча меняет границу «хорошего».

### Извлекающий (надо)

> «Извлеки факты» → структурный JSON:

```json
{
  "next_step":     "показ",
  "step_date":     "2026-07-31",
  "promise":       "call",
  "price_change":  8900000,
  "client_status": "торгуется",
  "facts_present": true
}
```

Почему это правильная форма:

- **Решение принимает код, а не модель.** Правило остаётся детерминированным
  и объяснимым: «обещан звонок 27-го, звонка нет» — это факт, а не мнение.
- **Результат проверяем.** Извлечённое обещание сверяется с телефонией
  и делами — данные уже собираются (`record["calls"]`, `deal_activities`).
- **Тестируется.** Точность извлечения по каждому полю меряется на золотом
  наборе. Появляется регрессионный тест на смену модели.
- **Не спорится.** Модель размечает текст, а не оценивает человека.
- **Устойчиво к подделке.** Чтобы «понравиться» извлекателю, надо написать
  конкретный факт с датой — то есть сделать работу.

**Это тот же принцип, что и в `SELLERS-COMMENT-QUALITY.md`: не наказывать
за комментарий, а не засчитывать его. LLM здесь — не судья, а парсер.**

## Часть 2. Какая модель

### Рекомендация: DeepSeek, уже подключённая

Задача — извлечь 3–5 полей из одного-двух предложений на русском. Это
**разметка, а не рассуждение**: с ней справляется практически любая
современная модель, включая дешёвые. Платить за «умную» модель здесь не за что.

Аргументы против смены:
- уже интегрирована (`langchain-openai`, ключ, два рабочих места вызова);
- объём большой — комментарии всех сделок, дважды в день, — а значит цена
  за токен важнее качества рассуждений;
- второй провайдер = второй ключ, второй режим отказа, вторая статья расходов
  и второй источник различий в поведении.

### Когда пересматривать

| Сигнал | Что делать |
|---|---|
| Точность извлечения на золотом наборе < 90 % | Сначала проверить промпт и JSON-схему — виноваты обычно они. Только потом модель посильнее |
| Требования по ПДн запрещают внешнего провайдера | Локальная модель класса 7–14B справится с извлечением. Но это отдельный проект: железо, инференс, поддержка |
| Цена вышла за бюджет | Почти наверняка не хватает кэша — см. часть 3, пункт 1 |

**Оговорка.** Конкретные версии моделей и цены нужно проверить на момент
принятия решения по актуальному прайсу провайдера — здесь они намеренно
не указаны, потому что устаревают быстрее, чем документ.

## Часть 3. Что важнее выбора модели

Всё ниже — по факту текущего кода.

### 1. Кэш по хэшу текста

Комментарий **неизменяем**. Анализировать его заново каждые 12 часов — чистая
потеря денег.

Механизм в проекте уже есть: `client_state.py` кэширует по `content_hash`
(`client_state.py:389`, поле в таблице — `db.py:330`). `lead_quality_audit.py`
им не пользуется.

Для комментариев кэш попадает почти всегда: новых комментариев за прогон —
единицы процентов от общего числа. **Это, вероятно, экономия больше 90 %,
и она не зависит от выбора модели.**

### 2. Структурированный вывод вместо выскабливания JSON из прозы

Сейчас `response_format` / `with_structured_output` не используются нигде.
JSON достают из текста регуляркой по ```-ограждению и `raw_decode`
(`lead_quality_audit.py:118`). В коде даже есть комментарий о наступленной
на этом баге:

> «raw_decode разбирает JSON-префикс и игнорирует хвост: одно лишнее слово
> после объекта раньше обнуляло весь чанк находок»

Это лечится JSON-схемой, а не более умной моделью. Заодно исчезает целый
класс тестов на разбор ответа.

### 3. Слоистость: LLM — только на остатке

LLM не должна видеть большинство комментариев. Порядок:

1. кэш — уже разобранные отсекаются;
2. повторы и сверка обещаний с фактами — считаются **без** LLM;
3. чёрный список чистого мусора — без LLM;
4. **LLM только на том, что осталось неоднозначным.**

Это и дешевле, и надёжнее: детерминированные слои не деградируют от смены
версии модели.

### 4. Отказ LLM не должен создавать нарушений

Если модель недоступна или вернула мусор — карточка помечается как
непрочитанная, нарушение **не создаётся**. Паттерн в проекте уже есть и ровно
для этого: `_evidence_incomplete` / `evidence_incomplete` (`tools.py:1430`)
с явным комментарием, что «нет комментария» и «не смог прочитать» — разные вещи.

Без этого сбой провайдера превратится в вал ложных нарушений, а для
переносимых правил — ещё и в переезд сделок в «Общую базу».

### 5. `temperature=0` для извлечения

Сейчас `0.1` (`lead_quality_audit.py:100`). Для разметки нужна
воспроизводимость: один и тот же комментарий обязан давать один и тот же
результат, иначе кэш и тесты теряют смысл.

## Часть 4. Персональные данные

Слой маскирования в проекте есть и сделан хорошо — `src/masking.py`,
включая склонение русских имён и варианты телефонов.

**Но у него есть граница, которую нужно проверить перед запуском на
комментариях.** Маска строится из полей карточки: имя контакта, телефоны,
почта. Комментарий брокера — свободный текст, куда руками может быть вписано
что угодно: адрес объекта, паспортные данные, сумма аванса, имя третьего лица,
которого нет в карточке.

Перед тем как отправлять комментарии внешнему провайдеру:
- проверить на реальной выгрузке, что остаётся в тексте после маскирования;
- при необходимости добавить маскирование адресов и документов;
- зафиксировать решение по 152-ФЗ — это вопрос к юристу, не к разработчику.

## Часть 5. Как решить эмпирически (примерно день работы)

Спорить о моделях дешевле один раз и на данных.

1. **Золотой набор.** 200 реальных комментариев из выгрузки
   (`scripts/export_sellers_deals_with_timeline_to_csv.py`), размеченных
   вручную — лучше двумя РОПами независимо, расхождения обсудить. Это же
   даст представление о том, насколько «содержательность» вообще
   договороспособна между людьми.
2. **Прогнать 2–3 модели** с одной и той же JSON-схемой.
3. **Мерить:** точность по каждому полю отдельно, цену на 1000 комментариев,
   задержку, долю невалидных ответов.
4. **Решение — по таблице.** Набор остаётся регрессионным тестом: при смене
   модели или промпта прогоняется заново.

Без этого набора любой выбор модели — угадывание, а любая последующая смена
версии — прыжок в темноте.

## Попутно: мёртвая настройка

`deepseek_v3_model` / `DEEPSEEK_V3_MODEL` (`config.py:41`, `.env.example:21`)
не читается нигде в коде — только объявлена и продублирована в примере
конфига. Значение совпадает с `deepseek_model`. Убрать либо задействовать:
две ручки, указывающие на одну модель, рано или поздно разъедутся и создадут
ложное ощущение, что где-то используется другая модель.
