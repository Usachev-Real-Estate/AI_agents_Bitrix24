# ИИ-агент контроля качества ведения CRM

План на основе решений от 2026-08-20.

**Статус: замеров ещё нет.** Инструмент разведки написан, но на портале
не запускался — у разработки нет доступа к боевому вебхуку. Запуск за вами,
все оценки объёмов и выбор модели ждут его результатов.

## Задача

Правила аудита проверяют **наличие** артефакта: комментарий есть, длина ≥ 30 символов,
дело запланировано. Брокеры оптимизировали ровно это. «Созвонился, договорились» —
правило удовлетворено, информации ноль. Никакая доработка регулярок это не чинит:
любой формальный критерий, который опубликован, удовлетворяется формально.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Цель v1 | Картина по клиентам для РОПа, а не оценка брокерам |
| Источник данных | Комментарии + дела + расшифровки звонков (BitrixGPT, включены у всех) |
| Объём | 500–2000 открытых карточек |
| Приватность | Маскировать ФИО, телефоны, почту; адреса и суммы оставить |
| Нагрузка на РОПа | 20–30 карточек в день |
| Приоритет в дайджесте | Смесь: сначала риск потери клиента, затем «непонятные» |
| Доставка | Личное сообщение каждому РОПу |
| Воронки | Два отдельных агента: покупатели (18) и продавцы (0) |
| Эталон качества | Ручная разметка 30–50 карточек |
| Модель | Старт на текущем DeepSeek; ключа RouterAI пока нет |

## Ключевая идея: качество как побочный продукт

Отдельного «оценщика по рубрике» не делаем. Рубрика превращается в чек-лист,
под который начинают писать, и через три месяца мы там же.

Вместо этого агент **восстанавливает состояние клиента**. Не смог восстановить —
это и есть оценка качества. Одна работа вместо двух: РОП получает то, что ему нужно
на самом деле, а «карточка неинформативна» становится выводом, который невозможно
нагенерить словами.

## Архитектура

### Инкрементальное состояние

Расшифровка звонка — 2–5 тысяч токенов, карточка с пятью звонками — 15–25 тысяч.
Гонять всю историю при каждом прогоне дорого и нестабильно: вывод «плавает»
от запуска к запуску.

Поэтому храним последнее состояние и при новом событии подаём модели только его
плюс новые события: «вот что мы знали, вот что произошло, обнови картину». История
сворачивается один раз и больше не пересылается.

### Схема ответа

```json
{
  "client_goal":   "что ищет: объект, бюджет, район, сроки, мотивация",
  "situation":     "что происходит сейчас",
  "last_event":    {"what": "...", "when": "2026-08-14"},
  "next_step":     {"what": "...", "when": "...", "who": "broker|client"},
  "blockers":      ["ипотека не одобрена"],
  "risk":          "low|medium|high",
  "recoverable":   true,
  "missing":       ["бюджет", "сроки"],
  "confidence":    0.0,
  "evidence":      ["дословная цитата из карточки"]
}
```

Два поля несут почти всю надёжность:

* **`evidence` — обязательные дословные цитаты.** Без требования подкреплять каждое
  утверждение цитатой модель сочинит правдоподобную историю клиента из воздуха.
  Цитаты заодно позволяют РОПу проверить вывод, не открывая карточку.
* **`missing` + `confidence` + право сказать «не знаю».** Модели по умолчанию
  заполняют пробелы. В промпте абстиненция поощряется явно, в схеме стоит дёшево.

### Особенности расшифровок Bitrix

Метод: `crm.activity.call.getTranscript(activityId)`, `activityId` берётся из
`crm.activity.list` с `TYPE_ID: 2`.

1. **Один запрос на звонок.** Карточка с пятью звонками — шесть дополнительных
   вызовов. При 500–2000 карточках это тысячи запросов и упор в лимиты Bitrix.
   Значит, тянуть один раз и кэшировать у себя.
2. **Спикеры не разделены**, таймкодов нет — сплошной текст. Модель определяет,
   кто говорит, по смыслу. В схеме нужно допускать «не удалось однозначно
   определить, кто это сказал», иначе агент припишет клиенту слова брокера.
3. **`null`, если расшифровки нет.** Отличать «звонок был, но не расшифрован»
   от «звонка не было» надо явно — иначе повторим ошибку с таймлайном, когда
   молчание принималось за отсутствие работы.

### Маскировка

Маскируем не универсальным распознаванием сущностей, а **по известным контактам
карточки**: берём ФИО, телефоны и почту из привязанных контактов и заменяем их
на устойчивые плейсхолдеры (`КЛИЕНТ_1`, `ТЕЛЕФОН_1`) — в том числе внутри текста
расшифровок, где имя звучит в разговоре. Обратная подстановка выполняется у нас,
при сборке дайджеста. Дёшево и надёжнее общего NER.

Шаг 6 важен архитектурно: правило наследует уже готовое — жизненный цикл нарушений,
дедупликацию, отчёты по отделам, рейтинг, команду `/мои`. Никакого параллельного
силоса.

## Шаг 0: разведка

Запускать на машине, где лежит боевой `.env` — скрипту нужен реальный вебхук.

```bash
python scripts/probe_transcripts.py --category 18 --limit 50 --fleet-size 1500
python scripts/probe_transcripts.py --category 0  --limit 50 --fleet-size 1500
```

Только чтение: ничего не меняет в CRM, не обращается к языковой модели и не сохраняет
тексты разговоров — считает покрытие и объёмы.

Отвечает на вопросы, без которых оценка стоимости остаётся гаданием: по скольким
звонкам реально отдаётся текст, сколько его приходится на карточку, во что обойдётся
полный проход и обычный день.

Пришлите вывод — от него зависят и выбор модели, и то, влезет ли карточка в контекст
целиком. До этого любые цифры стоимости будут выдуманными.

## Ловушки, которые надо держать в голове

**Гудхарт, круг второй.** Как только брокеры узнают, что комментарии читает ИИ, они
начнут писать для ИИ. Поэтому: оцениваем карточку целиком, а не отдельный комментарий;
рубрику как чек-лист не публикуем; первая версия помогает, а не наказывает.

**Слепое доверие агенту.** Единственная честная проверка — сверка с человеком.
Разметить 30–50 карточек, сравнить. Совпадение ниже ~80 % — доводим схему и промпт,
а не выкатываем. Дальше следить за корреляцией: карточки, помеченные «непонятно»,
должны чаще заканчиваться потерей клиента. Не коррелируют — измеряем не то.

**Не всё здесь задача для ИИ.** Если в карточке «созвонился, договорились», состояние
не восстановит никто. Бюджет, район, сроки, мотивация — это **поля**, а не свободный
текст. Заведёте полями — агенту останется то, в чём он силён: связная картина,
противоречия, риски.
