### 1.1. Лиды (Lead Analyst — `lead_analyst`)

#### Правило `lead_rule_1` — Лид в статусе «Новый» > 2 часов без комментария

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🐍 Детерминированный Python (`check_lead_rule1_violations`) |
| **Триггер** | `status_id == "NEW"` И `(current_time − date_create) > 2 часов` |
| **Проверка** | В `timeline` лида ищется хотя бы один комментарий от `assigned_by_id` (автор = ответственный, текст непустой). Если **нет** → нарушение |
| **Исключения** | Лиды со статусом `UC_H5GLEV` (Общие Лиды) — НЕ проверяются |
| **Данные** | `crm.lead.list` (поля: `ID, STATUS_ID, ASSIGNED_BY_ID, DATE_CREATE`), `crm.timeline.comment.list` |
| **Пример reason** | «Лид находится в статусе «Новый» более 2 часов, необходимо квалифицировать лида. (прошло 5 часов)» |

#### Правило `lead_rule_2` — Лид в статусе «Спам» без обоснования

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🤖 DeepSeek LLM (`LEAD_ANALYST_PROMPT`) |
| **Триггер** | `status_id` содержит `"JUNK"` (или legacy `"SPAM"`) |
| **Проверка (LLM)** | В `timeline` ищется комментарий с обоснованием причины спама длиной > 5 символов от любого пользователя. Если текст = `"спам"` / `"СПАМ"` / `"Спам"` (ровно это слово) — считается обоснованием, нарушения НЕТ |
| **Исключения** | Нет |
| **Данные** | `crm.lead.list` + `crm.timeline.comment.list` → отправляется в LLM чанками по 100 |
| **Пример reason** | «Лид переведен в статус «Спам» без указания причины в карточке.» |

#### Правило `lead_rule_3` — Лид в статусе «Нецелевой» без обоснования

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🤖 DeepSeek LLM (`LEAD_ANALYST_PROMPT`) |
| **Триггер** | `status_id` НЕ входит в список пропуска: `NEW`, `JUNK`, `WON`, `LOSE`, `CONVERTED` (Квалифицирован), `UC_52VG81` (Агент), `UC_H5GLEV` (Общие Лиды). Также `status_name` НЕ содержит «Агент» |
| **Проверка (LLM)** | В `timeline` ИЛИ `comments_field` ищется текст с обоснованием длиной > 5 символов. Если есть → нарушения НЕТ |
| **Исключения** | `CONVERTED` (Квалифицирован), `AGENT`, `UC_52VG81`, `UC_H5GLEV`, `NEW`, `JUNK`, `WON`, `LOSE` |
| **Данные** | `crm.lead.list` + `crm.timeline.comment.list` → LLM чанками по 100 |
| **Пример reason** | «Лид переведен в статус «Нецелевой» без указания причины в карточке.» |

### 1.2. Пропущенные звонки по лидам (`missed_calls_controller`)

#### Правило `lead_missed_callback` — Пропущенный звонок по лиду без обратного

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴🔴 very high |
| **Метод проверки** | 🐍 Детерминированный Python (`check_missed_callback_violations`) |
| **Триггер** | В `calls[]` лида есть хотя бы один звонок со `status == "missed"` |
| **Алгоритм** | 1. Сортируем все звонки лида по `start_date`. 2. Находим **последний** пропущенный (индекс `i`). 3. Проверяем: есть ли **после** него (индекс > `i`) звонок с `call_type == "outgoing"`? 4. Если **нет** → нарушение |
| **Исключения** | Лиды в статусах `CONVERTED` (Квалифицирован) и `UC_H5GLEV` (Общие Лиды) — НЕ проверяются |
| **Данные** | `voximplant.statistic.get` → если пусто → `crm.activity.list` (PROVIDER_TYPE_ID=CALL, RESPONSIBLE_ID). Кешируется по `user_id` |
| **Пример reason** | «Пропущенный звонок без обратного» |

### 1.3. Сделки покупателей (`buyer_deal_analyst`)

Все 5 правил — детерминированные, без LLM. Срабатывает ровно одно правило на сделку (определяется по `audit_rule` = маппинг `stage_id → 1…5`).

**Маппинг стадий (`BUYERS_STAGE_AUDIT_RULE`):**

| `stage_id` | Этап | `audit_rule` |
|-----------|------|-------------|
| `C18:NEW` | Первый контакт | 1 |
| `C18:UC_V0DMMX` | Подбор | 2 |
| `C18:UC_UFPFKK` | Показ | 3 |
| `C18:UC_A15GLR` | Показ проведен | 4 |
| `C18:LOSE` | Отложенный спрос | 5 |
| Остальные | Переговоры/Дожим/Офер/Задаток/Сделка/Агент/Проиграна | Нет аудита |

#### Правило `buyer_stage_1` — Сделка на этапе «Первый контакт» > 1 дня

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 1` И `days_on_stage > 1` |
| **Проверка** | `days_on_stage = (now − date_create) / 86400`. Если > 1 → нарушение |
| **Пример reason** | «Сделка находится на этапе «Первый контакт» более 1 дня.» |

#### Правило `buyer_stage_2` — Сделка на этапе «Подбор» без комментария > 5 дней

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 2` И `days_since_last_any_comment > 5` |
| **Проверка** | Ищется **последний** комментарий от **любого** автора в `timeline`. Разница с `now` > 5 дней → нарушение |
| **Особый случай** | Если комментариев нет вообще → `days = 999` → reason: «На этапе «Подбор» нет комментариев.» |
| **Пример reason** | «На этапе «Подбор» последний комментарий более 12 дней назад.» |

#### Правило `buyer_stage_3` — Сделка на этапе «Показ» без комментария > 3 дней

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 3` И `days_since_last_any_comment > 3` |
| **Проверка** | Аналогично `buyer_stage_2`, но порог = 3 дня |
| **Пример reason** | «На этапе «Показ» последний комментарий более 7 дней назад.» |

#### Правило `buyer_stage_4` — Сделка на этапе «Показ проведен» без комментария > 5 дней

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 4` И `days_since_last_any_comment > 5` |
| **Проверка** | Аналогично `buyer_stage_2`, порог = 5 дней |
| **Пример reason** | «На этапе «Показ проведен» последний комментарий более 8 дней назад.» |

#### Правило `buyer_stage_5` — Сделка в «Отложенном спросе» без комментария ответственного > 7 дней

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 5` И `days_since_last_comment_from_assigned > 7` |
| **Проверка** | Ищется **последний** комментарий от **`assigned_by_id`** (ответственного). Разница с `now` > 7 дней → нарушение |
| **Отличие от rule 2/3/4** | Проверяется комментарий **только ответственного**, а не любого автора |
| **Пример reason** | «На этапе «Отложенный спрос» нет комментария ответственного более 7 дней.» |

### 1.5. Сделки продавцов (`seller_deal_analyst`)

Воронка `CATEGORY_ID=0`. Платные источники: `24` (КЦ - 5%), `25` (Диспозл 10%), `26` (Диспозл 5%) — в текстах нарушений отделам **не пишем**.
В чатах отделов: блок «Сделки продавцов», синие иконки (🔵 / 🟦). Сводка по правилам продавцов — только админу в личный чат.

#### Правило `seller_meeting_no_outgoing` — «Назначение встречи» > 24 ч без исходящего

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔵 high |
| **Метод** | 🐍 Python (`check_seller_deal_violations`) |
| **Триггер** | `STAGE_ID=NEW` И `SOURCE_ID ∈ {24,25,26}` И возраст > 24 ч И нет исходящего звонка по сделке И нет комментария ответственного/РОПа |
| **Исключение** | Есть комментарий брокера или РОПа → нарушение **не** засчитывается |

#### Правило `seller_meeting_not_advanced` — есть исходящий, но сделка всё ещё на «Назначение встречи»

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔵 high |
| **Метод** | 🐍 Python |
| **Триггер** | `STAGE_ID=NEW` И paid source И есть исходящий звонок → нужно перевести дальше |

#### Правило `seller_deferred_no_comment` — «Отложенная продажа» без комментария

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟦 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `STAGE_ID=LOSE` И нет комментария от ответственного/РОПа |

#### Правило `seller_source_no_outgoing` — платный источник без исходящего (не NEW)

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔵 high |
| **Метод** | 🐍 Python |
| **Триггер** | paid source И возраст > 24 ч И нет исходящего И нет комментария ответственного/РОПа; на `NEW` не дублируется (там rule meeting_*) |
| **Исключение** | Есть комментарий брокера или РОПа → нарушение **не** засчитывается |

## 2. Weekly Broker Report (`src/weekly_report.py`)

**Не добавляет новых правил** — агрегирует нарушения из БД (таблица `violations`), собранные основным аудитом. Фильтр: только `routine` запуски (`is_routine = 1`), за последние 7 дней.

### Логика группировки

| Группа | Условие |
|--------|---------|
| 🔴 Нарушители | `COUNT(violations) > 0` за неделю |
| 🟢 Чистые | `violations IS NULL` за неделю И (`lead_count > 0` ИЛИ `deal_count > 0`) |

### Классификация нарушений для отображения

```sql
lead_violations      = COUNT(entity_type='lead' AND rule NOT LIKE '%missed%')
deal_violations      = COUNT(entity_type='deal' AND rule NOT LIKE '%missed%')
missed_call_violations = COUNT(rule LIKE '%missed_callback%')
```

### Рекомендации (`RULE_ADVICE`)

Для каждого нарушителя показываются рекомендации на основе типов правил, которые он нарушал:

| `rule` | Рекомендация |
|--------|-------------|
| `lead_rule_1` | обратить внимание на скорость квалификации лидов (статус «Новый» > 2 часов) |
| `lead_rule_2` | указывать причину перевода лида в «Спам» (JUNK) |
| `lead_rule_3` | указывать причину перевода лида в нецелевые |
| `lead_missed_callback` | не пропускать входящие звонки по лидам без обратного |
| `buyer_stage_1` | не задерживать сделки на этапе «Первый контакт» более 1 дня (стадия снята) |
| `buyer_stage_2` | добавлять комментарии к сделкам на этапе «Подбор» (раз в 5 дней) |
| `buyer_stage_3` | добавлять комментарии к сделкам на этапе «Показ» (раз в 3 дня) |
| `buyer_stage_4` | не забывать комментировать сделки на этапах Переговоры / Дожим / Офер / Задаток / Сделка |
| `buyer_stage_5` | регулярно комментировать сделки в «Отложенном спросе» |
| `buyer_missed_callback` | не пропускать входящие звонки по сделкам без обратного |

## 3. Broker Scorecard (`src/broker_score.py`)

**Не добавляет новых правил.** Агрегирует из БД (`violations` за 30 дней) + сравнивает с KPI по собственникам.

### Scoring-алгоритм

| Критерий | 🟢 Хорошо | 🟡 Средне | 🔴 Плохо |
|-----------|-----------|-----------|----------|
| **Нарушения CRM** (за 30 дней) | 0–2 | 3–5 | 6+ |
| **Собственники** (KPI = `OWNER_KPI_TARGET`) | ≥ target | ≥ target/2 | < target/2 |

**Итоговая оценка:**
- 🟢 + 🟢 → 🟢 **ОТЛИЧНО**
- 🔴 + 🔴 → 🔴 **ПЛОХО**
- Всё остальное → 🟡 **СРЕДНЕ**

## 4. Owner Tracker (`src/owner_tracker.py`)

**Не фиксирует нарушения.** Это информационный отчёт. Показывает:

- Количество новых контактов типа «Собственник» (`TYPE_ID = CONTACT_OWNER_TYPE_ID`) на каждого брокера
- KPI за текущий месяц: `текущие / OWNER_KPI_TARGET`
- Брокеры с 0 собственников помечаются `⚠️`

**Данные:** `crm.contact.list` (filter: `TYPE_ID`, `>=DATE_CREATE = OWNER_KPI_SINCE`)

## 5. Task Auditor (`src/task_auditor.py`)

### Правило фиксации просроченных задач

| Параметр | Значение |
|-----------|----------|
| **Что считается просрочкой** | `deadline < now` И `status ∈ [2, 3, 4]` (принята, выполняется, на проверке) |
| **Метод** | 🐍 Python (`classify_tasks`) |
| **Триггер** | Задача с `RESPONSIBLE_ID = user_id`, `REAL_STATUS ∈ [2, 3, 4]`, `deadline` в прошлом |
| **Проверка** | `(now − deadline).days` → `days_overdue`, минимум 1 день |
| **Исключения** | Пользователи из `TASK_AUDITOR_EXCLUDE_USERS_JSON` (Агентство Недвижимости, Вера Волкова, Светлана Щербакова, Марина Володина) |
| **Данные** | `tasks.task.list` для пользователей бэк-офиса (по `UF_DEPARTMENT`) и РОПов (по `WORK_POSITION`) |

### Группы сотрудников

| Группа | Как определяется |
|--------|-----------------|
| **Бэк-Офис** | `user.get` с filter `UF_DEPARTMENT = BACK_OFFICE_DEPT_ID` |
| **РОПы** | `user.get` с filter `WORK_POSITION = "Руководитель отдела продаж (РОП)"` |

## Фильтры, применяемые ко всем нарушениям

1. **`entity_id == 0`** — удаляются (некорректные данные)
2. **Неактивные пользователи** (`ACTIVE = false / "N"`) — исключаются из отчётов
3. **Отдел «Бэк-офис»** — нарушения не показываются (но в БД сохраняются)
4. **Дедупликация** — одно нарушение = уникальная комбинация `(entity_type, entity_id, rule)` на один аудит
5. **`is_routine = 0`** — исторические/массовые прогоны не попадают в weekly report
