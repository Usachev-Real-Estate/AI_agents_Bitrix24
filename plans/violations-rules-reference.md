### 1.1. Лиды (Lead Analyst — `lead_analyst`)

#### Правило `lead_rule_1` — Лид в статусе «Новый» > 2 часов без комментария

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🐍 Детерминированный Python (`check_lead_rule1_violations`) |
| **Триггер** | `status_id == "NEW"` И `(current_time − date_create) > 2 часов` |
| **Проверка** | В `timeline` лида ищется хотя бы один комментарий от `assigned_by_id` (автор = ответственный, текст непустой). Если **нет** → нарушение |
| **Исключения** | Лиды со статусом `UC_H5GLEV` (Общие Лиды) — НЕ проверяются |
| **Данные** | `crm.lead.list` (поля: `ID, STATUS_ID, ASSIGNED_BY_ID, DATE_CREATE`), `crm.timeline.comment.list` |
| **Пример reason** | «Лид находится в статусе «Новый» более 2 часов, необходимо квалифицировать лида. (прошло 5 часов)» |

#### Правило `lead_new_over_24h` — Лид «Новый» > 24 часов → «Общие лиды»

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод** | 🐍 Python (`process_stale_new_leads` + `move_lead_to_shared_pool`) |
| **Триггер** | `status_id == "NEW"` И `(now − date_create) > 24 часов` |
| **Действие** | `crm.lead.update` `STATUS_ID=1` («Общие лиды»). `ASSIGNED_BY_ID` **не** меняется. Учитывает `DRY_RUN`. |
| **Отчёт** | Факт перевода, `dry_run_skipped` или ошибка мутации |

#### Правило `lead_rule_2` — Лид в статусе «Спам» без обоснования

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🐍 Python (`check_lead_rule2_rule3_violations`) |
| **Триггер** | `status_id` = `"JUNK"` (или legacy содержит `"SPAM"`) |
| **Проверка** | В `timeline` ищется комментарий с обоснованием длиной > 5 символов. Если текст = `"спам"` / `"spam"` (ровно это слово) — считается обоснованием, нарушения НЕТ. Поле `COMMENTS` для rule_2 **не** учитывается |
| **Исключения** | Нет |
| **Данные** | `crm.lead.list` + `crm.timeline.comment.list` |
| **Пример reason** | «Лид переведен в статус «Спам» без указания причины в карточке.» |

#### Правило `lead_rule_3` — Лид в статусе «Нецелевой» без обоснования

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод проверки** | 🐍 Python (`check_lead_rule2_rule3_violations`) |
| **Триггер** | `status_id` НЕ входит в список пропуска: `NEW`, `JUNK`/`SPAM`, `WON`, `LOSE`, `CONVERTED`, `UC_52VG81` (Агент), `1` (Общие Лиды). Также `status_name` НЕ содержит «Агент» |
| **Проверка** | В `timeline` ИЛИ `comments_field` (в т.ч. BitrixGPT) текст длиной > 5 символов → нарушения НЕТ |
| **Исключения** | `CONVERTED`, `UC_52VG81`, `1`, `NEW`, `JUNK`, `WON`, `LOSE` |
| **Данные** | `crm.lead.list` + `crm.timeline.comment.list` + поле `COMMENTS` |
| **Пример reason** | «Лид переведен в статус «Нецелевой» без указания причины в карточке.» |

#### Правило `lead_leaked` — слитый лид (отдельный job)

### 1.2. Пропущенные звонки по лидам (`missed_calls_controller`)

#### Правило `lead_missed_callback` — Пропущенный звонок по лиду без обратного

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴🔴 very high |
| **Метод проверки** | 🐍 Детерминированный Python (`check_missed_callback_violations`) |
| **Триггер** | В `calls[]` лида есть хотя бы один звонок со `status == "missed"` |
| **Алгоритм** | 1. Сортируем все звонки лида по `start_date`. 2. Находим **последний** пропущенный (индекс `i`). 3. Проверяем: есть ли **после** него (индекс > `i`) звонок с `call_type == "outgoing"`? 4. Если **нет** → нарушение |
| **Исключения** | Лиды в статусах `CONVERTED` (Квалифицирован) и `UC_H5GLEV` (Общие Лиды) — НЕ проверяются |
| **Данные** | `voximplant.statistic.get` → если пусто → `crm.activity.list` (PROVIDER_TYPE_ID=CALL, RESPONSIBLE_ID). Кешируется по `user_id` |
| **Пример reason** | «Пропущенный звонок без обратного» |

### 1.3. Сделки покупателей (`buyer_deal_analyst`)

Все 5 правил — детерминированные, без LLM. Срабатывает ровно одно правило на сделку (определяется по `audit_rule` = маппинг `stage_id → 1…5`).

**Маппинг стадий (`BUYERS_STAGE_AUDIT_RULE`):**

| `stage_id` | Этап | `audit_rule` |
|-----------|------|-------------|
| `C18:NEW` | Подбор | 2 (+ `buyer_podbor_stale` если > 7 дн. на стадии) |
| `C18:UC_UFPFKK` | Первый показ | 3 |
| `C18:UC_DVW1P9` | Повторный показ | 3 |
| `C18:UC_8Z3SP6` | Офер | 6 |
| `C18:LOSE` | Отложенный спрос | 5 |
| `C18:APOLOGY` | Сделка проиграна | 7 |
| `C18:UC_2ZBA0G` | Агент | 8 |
| `C18:UC_RUCRAH` / `C18:UC_8X12HI` / WON | Задаток / Сделка / Договор | Нет аудита |

Дата входа на стадию: `crm.stagehistory.list` (`stage_entered_at`), fallback `DATE_CREATE`.

**Автоперенос:** нарушение этапа → «Общая база» / «Покупатели» (`C26:PREPARATION`). **Не переносим** (только отчёт РОПу): Офер, Сделка проиграна, пропущенные звонки, Задаток/Сделка. `ASSIGNED_BY_ID` не меняется. Учитывает `DRY_RUN` и `GENERAL_BASE_MOVE_AFTER`.

#### Правило `buyer_stage_1` — Сделка на этапе «Первый контакт» > 1 дня

| Параметр | Значение |
|-----------|----------|

| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 1` И `days_on_stage > 1` |
| **Проверка** | `days_on_stage = (now − date_create) / 86400`. Если > 1 → нарушение |
| **Статус** | Стадия снята с воронки; правило в коде оставлено, в маппинге не используется |
| **Пример reason** | «Сделка находится на этапе «Первый контакт» более 1 дня.» |

#### Правило `buyer_stage_2` — Сделка на этапе «Подбор» без комментария ответственного > 2 дней

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 2` И простой без комментария ответственного/РОПа > 2 дней |
| **Проверка** | Последний комментарий брокера (`assigned_by_id`) или его РОПа. Если таких нет — считаем от `DATE_CREATE` (`idle_days`), а не «999 дней». Если простой > 2 дней → нарушение |
| **Исключение** | Есть непросроченное дело «по связи с клиентом» **по этой сделке** → не флажим. Дела на контактах/других сущностях у того же ответственного не учитываются |
| **Пример reason** | «Сделка находится на этапе «Подбор» более 2 дней без комментария ответственного.» |

Дополнительно `buyer_podbor_stale`: на стадии «Подбор» > 7 дней (от `stage_entered_at`) — отдельное нарушение, даже если каденс комментария соблюдён.

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🔴 high |
| **Метод** | 🐍 Python |
| **Пример reason** | «На этапе «Первый показ» нет запланированного дела. В случае невыполнения требования регламента сделка будет перенесена в воронку «Общая база».» |

Комментарий брокера/РОПа >= 30 символов (чат не учитывается).

#### ~~Правило `buyer_stage_4`~~ — снято с воронки

Стадии Переговоры / Дожим больше не аудируются (`buyer_stage_4` в маппинге нет; код оставлен только для совместимости). Офер вынесен в `buyer_ofer_comment`.

#### Правило `buyer_stage_5` — «Отложенный спрос»: запланированное дело

| Параметр | Значение |
|-----------|----------|
| **Severity** | 🟡 medium |
| **Метод** | 🐍 Python |
| **Триггер** | `audit_rule == 5` (`C18:LOSE`) и нет **живого** (непросроченного) открытого дела по сделке |
| **Проверка** | Комментарии **не** учитываются. Нужно открытое дело на этой сделке; если все дела просрочены → нарушение |
| **Пример reason** | «На этапе «Отложенный спрос» нет запланированного дела.» |

#### Правила `buyer_lost_no_reason` / `buyer_agent_no_comment`

Коллектор дополнительно выбирает закрытые сделки на `APOLOGY` (не только `CLOSED=N`).

- **Проиграна** (`buyer_lost_no_reason` / `seller_lost_no_reason`): комментарий брокера/РОПа **любой давности** или дело брокера/РОПа. Нарушение только если нет ни комментария, ни дела.
- **Агент** (`buyer_agent_no_comment`): комментарий брокера/РОПа > 5 символов после входа на стадию или не раньше чем за 24 ч (`STAGE_COMMENT_LOOKBACK`). То же окно у `buyer_ofer_comment`.

### 1.5. Сделки продавцов (`seller_deal_analyst`)

Воронка `CATEGORY_ID=0` (все источники).
- **Назначение встречи:** комментарий брокера/РОПа **или** непросроченное дело в течение 24 ч с `DATE_CREATE`. За 2 ч до дедлайна — личное напоминание брокеру (не нарушение), если нет ни комментария, ни живого дела.
- **Переговоры / Закрытая продажа / Поиск клиента:** каденс по **комментарию** брокера/РОПа (дело не снимает).
- **Подготовка объекта в рекламу:** касание = комментарий **или** дело.
- **Закрытая продажа** и **Поиск клиента:** обязательно поле «ID объекта Афины» (`UF_CRM_1780911079` на сделках; у лидов другой код `UF_CRM_1780911032`).
- **Поиск клиента** никогда не переносится в «Общая база» (только предупреждение).
- **Автоперенос:** каденс / 14 дней Переговоры / Отложенная без дела → «Общая база» / «Продавцы» (`C26:NEW`). **Не переносим** (только отчёт РОПу): Проиграна, нет ID Афины, Поиск клиента, пропущенные звонки. `ASSIGNED_BY_ID` не меняется. Учитывает `DRY_RUN` и `GENERAL_BASE_MOVE_AFTER`.
Исходящий звонок **не** снимает нарушение.
В чатах отделов: блок «Сделки продавцов». Сводка по правилам продавцов и контроль Спам/Нецелевой — только админу в личный чат.

**Каденс (`SELLERS_STAGE_CADENCE`):** `NEW` — 24 ч, комментарий брокера/РОПа **или** непросроченное дело (за 2 ч до дедлайна — личное напоминание, не нарушение); `UC_KEOOG8` (Переговоры) — комментарий раз в 3 сут **и** не больше 14 дней на стадии; `FINAL_INVOICE` — касание (комментарий **или** дело) раз в 7 сут; `UC_A94BGF` / `UC_FADPBF` — комментарий раз в 7 сут + поле «ID Афины». Без аудита: `WON`. `APOLOGY` — комментарий брокера/РОПа любой давности **или** дело (`seller_lost_no_reason`). «Поиск клиента» никогда не переносится в «Общая база».

## 2. Weekly Broker Report (`src/weekly_report.py`)

**Не добавляет новых правил** — агрегирует нарушения из БД (таблица `violations`), собранные основным аудитом. Фильтр: только `routine` запуски (`is_routine = 1`), за последние 7 дней.

### Логика группировки

| Группа | Условие |
|--------|---------|
| 🔴 Нарушители | `COUNT(violations) > 0` за неделю |
| 🟢 Чистые | `violations IS NULL` за неделю И (`lead_count > 0` ИЛИ `deal_count > 0`) |

### Классификация нарушений для отображения

```sql
lead_violations      = COUNT(entity_type='lead' AND rule NOT LIKE '%missed%')
deal_violations      = COUNT(entity_type='deal' AND rule NOT LIKE '%missed%')
missed_call_violations = COUNT(rule LIKE '%missed_callback%')
```

### Рекомендации (`RULE_ADVICE`)

Для каждого нарушителя показываются рекомендации на основе типов правил, которые он нарушал:

| `rule` | Рекомендация |
|--------|-------------|
| `lead_rule_1` | обратить внимание на скорость квалификации лидов (статус «Новый» > 2 часов) |
| `lead_new_over_24h` | квалифицировать лид «Новый» за 24 часа, иначе он уйдёт в «Общие лиды» |
| `lead_rule_2` | указывать причину перевода лида в «Спам» (JUNK) |
| `lead_rule_3` | указывать причину перевода лида в нецелевые |
| `lead_missed_callback` | не пропускать входящие звонки по лидам без обратного |

## Фильтры, применяемые ко всем нарушениям

1. **`entity_id == 0`** — удаляются (некорректные данные)
2. **Неактивные пользователи** (`ACTIVE = false / "N"`) — исключаются из отчётов
3. **Отдел «Бэк-офис»** — нарушения не показываются (но в БД сохраняются)
4. **Дедупликация** — одно нарушение = уникальная комбинация `(entity_type, entity_id, rule)` на один аудит
5. **`is_routine = 0`** — исторические/массовые прогоны не попадают в weekly report
