# Деплой b24-ai-auditor на сервер

## 1. Подготовка сервера

```bash
# Установить Docker (если нет)
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
```

Перелогиньтесь или выполните `newgrp docker`, чтобы группа `docker` применилась.

## 2. Клонирование и настройка

```bash
cd /home
git clone https://github.com/Usachevofishial-git/AI_agents_Bitrix24.git Ai_agents_crm
cd Ai_agents_crm

# Создать .env из примера
cp .env.example .env
nano .env  # Вставить реальные ключи и URL
```

**Каталог на уже развёрнутой машине не угадывают, а спрашивают у Docker:**

```bash
docker inspect b24-dashboard \
    --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
```

Compose записывает в контейнер каталог, из которого его собрали, — это
единственный источник правды. Гадать по имени бесполезно: папка называется
не так, как репозиторий, а в этом документе до сентября 2026 стоял путь
`/opt/b24-ai-auditor`, которого на сервере нет вовсе. Поиски развёртывания
начинались с него и упирались в пустой `/opt`.

**Важно:** в `.env` установить:

- `DRY_RUN=false` — для боевого запуска (сообщения в чаты)
- `LOG_LEVEL=INFO`
- `REPORT_SINCE=2026-06-02` (или актуальную дату начала контроля)
- `B24_WEBHOOK_URL`, `DEEPSEEK_API_KEY`, `BUYERS_CATEGORY_ID`, `SELLERS_CATEGORY_ID`

Файл `.env` не коммитится в git — храните только на сервере.

## 3. Сборка Docker-образа

```bash
docker build -t b24-ai-auditor:latest .
```

## 4. Тестовый запуск

```bash
# Dry-run (без мутаций в CRM — DRY_RUN из .env или переопределение)
docker run --rm --env-file .env \
  -e DRY_RUN=true \
  -v $(pwd)/logs:/app/logs \
  b24-ai-auditor:latest

# Проверить логи
tail -100 logs/audit.log
```

В логах ожидаются: сбор лидов/сделок, аналитики, `report sent to ROP chat`, сводка в chat 22358.

## 5. Установка cron

Расписание: **10:00 и 17:00 МСК** (07:00 и 14:00 UTC), понедельник–пятница.

```bash
# Активировать crontab (в crontab.txt — вариант Docker)
crontab crontab.txt

# Проверить
crontab -l
```

Убедитесь, что каталог `logs/` существует и доступен для записи:

```bash
mkdir -p logs
```

## 6. Мониторинг

```bash
# Логи аудита
tail -f /home/Ai_agents_crm/logs/audit.log

# Логи cron
tail -f /home/Ai_agents_crm/logs/cron.log
```

## 7. Обновление

Сначала место: сборка занимает несколько гигабайт, и на заполненном диске она
падает на середине, оставляя сервис на старом образе.

```bash
df -h /                    # нужно хотя бы 5 ГБ свободных
docker builder prune -af   # если мало: кэш сборок сносится без последствий
```

Дальше — код и образы:

```bash
cd /home/Ai_agents_crm
git pull

# Cron-задачи: собирают образ по тегу, подхватят его при следующем запуске
docker build -t b24-ai-auditor:latest .

# Дашборд: отдельный контейнер, обновляется только с --build
docker compose up -d --build dashboard
curl -si localhost:8080/healthz     # {"status":"ok"}
```

Флаг `--build` обязателен. Без него `docker compose up -d` видит, что образ
сервиса уже есть, и просто перезапускает контейнер на старом коде — выкатка
выглядит успешной, а изменений на странице нет.

Схему витрины поднимает первый же запуск нового кода: и дашборд, и ETL зовут
`init_analytics_db()` на старте, а он сверяет `SCHEMA_VERSION` и досоздаёт
недостающие колонки. Отдельной команды для миграции нет и не нужно.

Новая колонка приходит пустой: витрина не перезапрашивает то, что уже
загружено. Описания дел (колонка «Что написали и что поставили» в «Движении»)
появятся после ближайшего полного прогона — он стоит в cron на 02:35 UTC
(05:35 МСК). Ждать ночь не обязательно, полный прогон можно позвать руками:

```bash
docker run --rm --env-file .env -v $(pwd)/logs:/app/logs -v $(pwd)/data:/app/data \
  b24-ai-auditor:latest python src/analytics/etl.py --full
```

## 7.1. Ротация логов

`logs/audit.log` ротирует сам Python (`RotatingFileHandler`, 10 МБ × 5).
`logs/cron.log` — это перенаправление `>>` из crontab, и за ним не следит
никто: пишут в него все задачи, а чат-поллер тикает каждую минуту. На боевом
сервере файл дорос до **14 ГБ при диске в 41** — то есть до трети места.
Кончится диск — встанет всё сразу: ETL, аудит, дашборд.

Установить ротацию (от root, один раз):

```bash
cp deploy/logrotate-b24 /etc/logrotate.d/b24-auditor
logrotate -d /etc/logrotate.d/b24-auditor    # проверка без изменений
logrotate -f /etc/logrotate.d/b24-auditor    # первый прогон принудительно
```

`copytruncate` в конфиге обязателен: cron держит файл открытым на дозапись, и
ротация переименованием оставила бы задачи писать в удалённый файл — место не
освободилось бы, а новый лог остался бы пустым.

Разово освободить место, не дожидаясь logrotate:

```bash
cd /home/Ai_agents_crm
tail -n 20000 logs/cron.log > logs/cron.log.tail
truncate -s 0 logs/cron.log
```

`truncate`, а не `rm`: удаление оставит место занятым, пока работающие задачи
держат файл открытым.

В `scripts/cron_job.sh` есть предохранитель на случай, когда logrotate не
установлен: при размере больше 1 ГБ лог обрезается до последних 50 МБ, и в
него пишется, почему это произошло. Это защита от переполнения диска, а не
замена ротации — порог намеренно высокий.

## 9. Выгрузка досье по сделкам

Отдельный от аудита модуль (`src/dossier.py`). Он ничего не оценивает и
ничего не меняет в CRM: собирает по каждой сделке всю историю работы —
комментарии с автором, дела, звонки с расшифровками, переходы стадий,
смены ответственного — и кладёт одной строкой JSONL на каждую сделку.
Оценку по этим данным делает внешняя модель.

### Переменные .env

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `DOSSIER_DIR` | `data/dossier` | куда складывать выгрузку |
| `DOSSIER_TRANSCRIPT_BUDGET` | `500` | потолок запросов расшифровок за прогон |
| `DOSSIER_LAUNCH_BUDGET` | `100` | потолок очереди на ручной запуск расшифровок |
| `DOSSIER_KEEP_FILES` | `30` | сколько выгрузок хранить |
| `GDRIVE_CREDENTIALS_FILE` | пусто | путь к ключу сервисного аккаунта |
| `GDRIVE_FOLDER_ID` | пусто | папка назначения в Drive |

Обе переменные Drive пустые — выгрузка остаётся в `DOSSIER_DIR`, и прогон
пишет об этом в лог. Отсутствие Drive доставку ломает, сбор — нет.

### Ключ Google

Ключ монтируется **отдельным томом только на чтение** и в `data/` не
кладётся: там базы, туда пишет всё подряд, и ключ доступа к общему диску
компании там быть не должен.

```bash
cd /home/Ai_agents_crm
# 1. Файл обязан существовать ДО первого запуска: Docker, не найдя его,
#    заведёт на его месте КАТАЛОГ, и ошибка всплывёт внутри библиотеки
#    Google, а не в понятной строке лога.
install -m 600 /dev/null deploy/gdrive.json
# 2. Положить в него ключ сервисного аккаунта (JSON из Google Cloud).
# 3. Расшарить папку назначения на почту из поля client_email этого файла
#    с правом редактирования — иначе Drive ответит 404 на ID папки, что
#    читается как «папки нет».
```

Если Drive не нужен вовсе, пустого файла достаточно: код проверяет, что по
пути лежит именно файл, и при пустых переменных к нему не обращается.

### Ручной прогон

```bash
DOSSIER="docker run --rm --env-file .env \
  -v $(pwd)/logs:/app/logs -v $(pwd)/data:/app/data \
  -v $(pwd)/deploy/gdrive.json:/app/deploy/gdrive.json:ro \
  b24-ai-auditor:latest python src/dossier.py"

# Проба на двадцати карточках — с неё и начинать
$DOSSIER --mode delta --limit 20

# Полный прогон
$DOSSIER --mode full

# Полный, включая закрытые сделки
$DOSSIER --mode full --include-closed
```

### Что появляется рядом с выгрузкой

| Файл | Что в нём |
|---|---|
| `delta_ГГГГ-ММ-ДД.jsonl` | строки досье |
| `delta_ГГГГ-ММ-ДД.meta.json` | время прогона, счётчики, список несобравшихся id |
| `queue_ГГГГ-ММ-ДД.json` | звонки, по которым стоит запустить расшифровку руками |
| `README.md` | правила чтения для модели; переписывается каждым прогоном |
| `assignee_snapshot.json` | снимок «сделка → ответственный» |
| `assignee_log.jsonl` | журнал смен ответственного |

**Последние два не удаляются уборкой и не восстанавливаются.** В REST
истории смены ответственного нет вовсе: журнал копится только вперёд, от
прогона к прогону. Потеряв его, восстановить, кто вёл карточку до нынешнего
брокера, будет нечем.

### Замер портфеля (18.09.2026)

Цифры, по которым выставлены бюджеты. Пересняты разведкой — если портфель
заметно вырастет, прогоните её заново.

| Что | Сколько |
|---|---|
| Открытых сделок | 1289 (375 покупатели + 914 продавцы) |
| Звонков по ним | 1645 |
| Длиннее минуты | 448 (27 %) |
| Отсечка снимает | 1197 обращений (73 %) |
| Из длинных уже с текстом | ~71 % (замер по выборке из 150) |
| Кандидатов в очередь на запуск | ~130 на весь портфель |

`DOSSIER_TRANSCRIPT_BUDGET = 500` покрывает все 448 длинных звонков за один
проход. Это условие, а не запас: незабранная расшифровка получает статус
`deferred`, а он означает «данных недостаточно», и при меньшем бюджете
полтораста карточек выглядели бы необъяснимыми в первом же прогоне.

### Очередь на расшифровку

Запуска расшифровки в REST нет — есть только чтение. Поэтому модуль
формирует очередь, а запускается она руками из браузерной сессии портала.
В очередь попадает звонок, у которого нет текста, длительность от 60 секунд
и карточка на активной стадии; первыми идут карточки, где ответственный не
написал ни одного комментария. Один и тот же звонок ставится в очередь не
больше двух раз и не чаще раза в сутки.

Разведка перед настройкой бюджетов — сколько звонков и у скольких есть
текст:

```bash
docker run --rm --env-file .env -v $(pwd)/data:/app/data \
  b24-ai-auditor:latest \
  python scripts/probe_transcripts.py --category 18 --category 0
```

### Cron

Пункты 22 и 23 в `crontab.txt`: ежедневный `delta` в 09:30 МСК (до
утреннего аудита) и недельный `full` по понедельникам в 03:00 МСК.

## 10. Напоминание по «Общим лидам»

Задача пишет брокеру личное сообщение с пометкой «важное» и пинг на
колокольчик: у вас столько-то лидов на этапе «Общие лиды», квалифицируйте.
Ничего в CRM не меняет — только читает `crm.lead.list` и шлёт сообщения.

### Включение

По умолчанию выключена. Строка в `crontab.txt` (пункт 24) стоит активной, но
каждый запуск сразу выходит по флагу и пишет об этом в лог. Чтобы рассылка
пошла, в `.env`:

```
SHARED_LEAD_REMINDER_ENABLED=true
SHARED_LEAD_REMINDER_START_HOUR=9
SHARED_LEAD_REMINDER_DEADLINE_HOUR=14
```

Посмотреть, кому и по каким лидам ушло бы сообщение, ничего не отправляя
(`DRY_RUN=true` — общий тумблер проекта, поэтому на боевом сервере его
передают разово, а не правят в `.env`; `--force` снимает проверку часов, но
не выключатель — без него проверка в неурочный час и в выходной просто
промолчит):

```bash
docker run --rm --env-file .env -e DRY_RUN=true -e SHARED_LEAD_REMINDER_ENABLED=true \
  -v $(pwd)/logs:/app/logs b24-ai-auditor:latest \
  python src/shared_lead_qualify_reminder.py --force
```

В логе будет строка `DRY_RUN: would notify user_id=... leads=[...]` на каждого
брокера: получатель и номера лидов. Сам текст сообщения в лог не пишется — он
целиком собирается в `format_chat_message`, и читать его надо там.

### Темп

Cron даёт пять тиков: 09:00–13:00 МСК по будням. Шаг часовой, потому что
отметок о прошлой отправке у задачи пока нет: на десятиминутном шаге брокер
получал бы тридцать «важных» сообщений за утро. Чтобы учащать, сначала нужна
память об отправленном — как в `buyer_commission_reminder` (`is_notify_due` +
таблица в `violations.db`).

Режим `--loop` в модуле оставлен для ручной отладки. Под `scripts/cron_job.sh`
его пускать нельзя: `flock` держится всё время работы процесса, и очередной
тик тихо выйдет с кодом 0.

### Что задача не делает

Ответственного у лида не меняет — ни она, ни что-либо ещё в репозитории:
`ASSIGNED_BY_ID` у лида не пишет ни один модуль. Переводов статуса два —
`move_lead_to_shared_pool` («Новый» → «Общие лиды», ответственного не
трогает) и разовый импорт `scripts/fill_cian_leads_from_csv.py`, который
правит поля карточки, но не ответственного. Дедлайн 14:00 в тексте
сообщения — это договорённость с людьми, а не действие системы.

Неуспехом для cron считается только настоящий сбой: портал не отдал лиды или
список активных, либо отправка кому-то не удалась. Тихий прогон по
расписанию (выключено, выходной, вне окна) выходит нулём и админа не будит.

# Аналитический дашборд (pars.afina-crm.ru/dashboard)

Отдельный веб-сервис в том же образе: витрина `data/analytics.db`, наполняемая
ETL из Bitrix24, и FastAPI поверх неё. Дашборд читает витрину, а не Bitrix,
поэтому открывается за миллисекунды и не нагружает портал при просмотре.

## 1. Настройка

Сгенерировать ключ подписи сессий и дописать в `.env`:

```bash
python src/web/manage.py gen-secret >> .env
```

Проверить в `.env`:

- `DASHBOARD_SECRET_KEY` — заполнен (без него сервис не стартует, и это
  намеренно: генерация ключа при запуске разлогинивала бы всех при рестарте);
- `DASHBOARD_COOKIE_SECURE=true` — обязательно в проде;
- `ANALYTICS_MONTHS_BACK=12` — глубина истории.

Раздел «Объекты» тянет данные из Афины CRM и включается отдельно. Без ключа
его нет ни в меню, ни по прямому адресу — остальной дашборд при этом работает
как обычно:

- `AFINA_API_BASE_URL=https://afina-crm.ru`;
- `AFINA_API_KEY` — значение `PUBLIC_API_KEY` со стороны Афины, тот же ключ,
  что у публичного каталога сайта.

Проверить ключ до запуска дашборда:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "X-API-Key: $AFINA_API_KEY" \
  https://afina-crm.ru/api/public/dashboard/summary        # 200
```

`401` — ключ не тот; `503` — `PUBLIC_API_KEY` не задан на стороне Афины;
`404` — витрины по этому адресу нет: адрес ведёт на другой сервис, в нём
лишний путь, либо бэкенд Афины не пересобран.
Списка разрешённых origin (`FRONTEND_URLS`) правка не требует: в Афину ходит
сервер дашборда, а не браузер.

## 2. Первичная загрузка витрины

Сначала проверить доступность API и поддержку истории стадий лидов:

```bash
docker run --rm --env-file .env -v $(pwd)/data:/app/data \
  b24-ai-auditor:latest python src/analytics/etl.py --probe
```

Затем бэкфилл за 12 месяцев. Идёт десятки минут — это разовая операция:

```bash
docker run --rm --env-file .env -v $(pwd)/logs:/app/logs -v $(pwd)/data:/app/data \
  b24-ai-auditor:latest python src/analytics/etl.py --backfill
```

## 3. Пользователи и разграничение доступа

Две роли:

| Роль | Что видит |
|---|---|
| `admin` | всю компанию, все воронки, все отделы |
| `rop` | только назначенные ему отделы |

То же самое умеет раздел **«Доступы»** на самом дашборде — он доступен
администратору и не требует ssh. Онбординг брокера и особенно закрытие
доступа уволенному нужны в ту минуту, когда о них вспомнили, а не когда до
сервера дойдут руки. Команды ниже остаются: первого администратора заводить
всё равно нечем, кроме них.

Пароль читается из потока ввода и никогда не передаётся аргументом командной
строки: аргумент осел бы в истории шелла и был бы виден в `ps`. В разделе
«Доступы» пароль придумывает браузер и показывает один раз до отправки
формы — в ответе сервера его нет.

```bash
DOCKER="docker run --rm -it --env-file .env -v $(pwd)/data:/app/data b24-ai-auditor:latest"

# какие отделы есть в витрине, какие у них ID и кто ими руководит
$DOCKER python src/web/manage.py departments

# администратор — роль указывается явно
$DOCKER python src/web/manage.py adduser director --role admin

# РОП: отделы берутся из витрины по фамилии
$DOCKER python src/web/manage.py adduser trofimova --role rop --rop Трофимова

# то же самое числами, если фамилии в списке агентства нет
$DOCKER python src/web/manage.py adduser komdir --role rop --department 44 --department 50

# кто что видит
$DOCKER python src/web/manage.py list

# сменить права; действует немедленно, перелогин не нужен
$DOCKER python src/web/manage.py setrole trofimova --role rop --department 44 --department 60

# сменить пароль; прежние сессии человека закрываются
$DOCKER python src/web/manage.py passwd trofimova
```

`passwd` меняет ТОЛЬКО пароль. Роль, отделы и имя остаются: раньше он звал
`create_user`, а та на существующем логине переписывает строку целиком —
директор, попросивший сменить пароль, становился РОПом без отделов, и
заметить это можно было только по пустому дашборду.

**Роль по умолчанию — `rop` без отделов, то есть «не видит ничего».** Забытый
флаг создаёт пользователя с минимальным доступом, а не администратора: ошибка
в сторону меньшего доступа исправляется одной командой, обратная
обнаруживается по утёкшим данным.

`--rop ФАМИЛИЯ` берёт отделы из витрины по списку фамилий РОПов
(`src/qc_delivery.py`, решение агентства от 31.08) — по тому же списку
рассылается отчёт QC, и расходиться этим двум ответам на вопрос «чей это
отдел» нельзя. Фамилии нет в списке, под ней в портале двое или ETL ещё не
прогонялся — команда падает и просит указать отделы числами: учётка,
собранная по догадке, открыла бы РОПу чужой отдел.

### Кадровые изменения в Bitrix

Отдел сделки — это отдел её **текущего** ответственного: истории назначений
Bitrix не отдаёт. Отсюда три следствия, о которых стоит знать заранее.

| Что произошло в Bitrix | Когда видно на дашборде | Что происходит |
|---|---|---|
| Нанят менеджер | в течение 15 минут | до обновления справочника его сделки не принадлежат ни одному отделу: их видит только администратор, РОП — нет |
| Менеджер переведён в другой отдел | в течение 15 минут | **все** его сделки, включая прошлые месяцы, переезжают в новый отдел вместе с историей движения |
| Менеджер уволен | остаётся как был | строки из справочника не удаляются, сделки продолжают числиться за последним известным отделом |

Справочник людей обновляется в каждой 15-минутной догрузке (это 4 запроса,
около 0,2% суточного лимита портала). Стадии и воронки — только в ночной
сверке: они меняются несравнимо реже, а стоят два десятка запросов.

Про переезд истории стоит предупредить РОПов: после перевода сотрудника
прошлые отчёты по отделу изменятся задним числом. Отдел, из которого ушёл
человек, «потеряет» его прошлые сделки, а принявший — «приобретёт». Так
устроено потому, что снимков состава отделов по датам взять неоткуда;
хранить их — отдельная задача, если такая точность понадобится.

Карточка без ответственного не принадлежит ни одному отделу — её видит только
администратор, а «Качество данных» считает такие карточки отдельной строкой.

Прочие команды: `passwd` (меняет пароль и отзывает все сессии), `disable`,
`enable`, `sessions`, `revoke`, `purge`.

### Как устроено ограничение

Область видимости задаётся **один раз при открытии соединения** с витриной, а
не подставляется фильтром в каждый запрос. Поверх таблиц создаются временные
представления `v_deal` / `v_lead` / `v_stage_event` / `v_user`, уже суженные до
разрешённых отделов, и метрики обращаются только к ним. Новый запрос получает
ограничение автоматически — забыть его невозможно, потому что забывать нечего.
Обращение к таблицам напрямую запрещено и проверяется тестом.

## 4. Запуск сервиса

```bash
docker compose up -d dashboard
docker compose logs -f dashboard
curl -s localhost:8080/healthz     # {"status":"ok"}
```

Сервис слушает только `127.0.0.1:8080` на хосте. Публиковать порт как
`8080:8080` нельзя: Docker пробивает такую публикацию мимо ufw через цепочку
`DOCKER-USER`, и дашборд оказывается в интернете без TLS.

## 5. nginx и TLS

```bash
cp deploy/nginx-dashboard.conf /etc/nginx/sites-available/pars.afina-crm.ru
ln -s /etc/nginx/sites-available/pars.afina-crm.ru /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
certbot --nginx -d pars.afina-crm.ru
```

Наружу отдаются только `/dashboard/` и `/healthz`; остальные пути — 404.

## 6. Регулярное обновление данных

Две задачи уже есть в `crontab.txt` (пункты 15 и 16):

| Задача | Расписание | Зачем |
|---|---|---|
| `etl.py --incremental` | каждые 15 мин | догрузка изменённого |
| `etl.py --full` | 05:30 МСК | полная сверка + вычисление удалённых |

Полная сверка обязательна: инкремент по `DATE_MODIFY` принципиально не видит
удалений, и без неё удалённая сделка навсегда осталась бы в счётчиках воронки.

## 8. Диагностика

| Симптом | Куда смотреть |
|---|---|
| «Витрина пуста» на всех страницах | ETL ни разу не отработал: `--backfill` |
| «Данные загружались N минут назад» | упала cron-задача: `tail logs/cron.log` |
| Суммы кажутся маленькими | «Качество данных» → покрытие поля «Комиссия» |
| Не сходится с Bitrix | «Качество данных» → «Сходимость», проверить окно витрины |
| Сервис не стартует | `docker compose logs dashboard` — скорее всего пустой `DASHBOARD_SECRET_KEY` |
| РОП видит пустой дашборд | `manage.py list` — вероятно, не назначены отделы |
| РОП не видит часть своих сделок | у них другой текущий ответственный; проверьте в Bitrix |
| Нет пункта «Объекты» | пустой `AFINA_API_KEY` либо вход не администратором |
| «Афина не приняла ключ» | `AFINA_API_KEY` разошёлся с `PUBLIC_API_KEY` Афины |
| «На стороне Афины не настроен PUBLIC_API_KEY» | задать его в `.env` Афины |
| «По этому адресу витрины Афины нет» | другой сервис, лишний путь в адресе или непересобранный бэкенд |
| «Адрес Афины разобрать не удалось» | опечатка в `AFINA_API_BASE_URL` |
| «Афина не ответила за N с» | Афина недоступна или медленна: `AFINA_API_TIMEOUT_SECONDS` |
| «Имя … не разрешается в адрес» | контейнер дашборда не резолвит имя: DNS или опечатка |
| «Афина отказала в соединении» | адрес недоступен именно с сервера дашборда — см. ниже |
| «Сертификат Афины не принят» | цепочка сертификатов или разъехавшееся время на сервере |
| «ушёл через прокси и не дошёл» | `HTTP_PROXY` / `HTTPS_PROXY` в окружении дашборда |

Если Афина живёт на том же сервере, что и дашборд, публичный адрес изнутри
контейнера может не открываться: пакет уходит наружу и должен вернуться на тот
же хост, а такой разворот разрешён не везде. Симптом — «Афина отказала в
соединении» при том, что снаружи `curl` до неё доходит. Лечится внутренним
адресом в `AFINA_API_BASE_URL`: имя контейнера Афины, если сети общие
(`http://athena-backend-1:8000`), либо адрес docker-моста
(`http://172.17.0.1:<порт>`).

Разобрать по шагам, где именно рвётся, — прямо в контейнере дашборда:

```bash
docker compose exec dashboard python scripts/afina_selfcheck.py

# перебрать кандидатов, не правя .env и не перезапуская контейнер:
docker compose exec dashboard python scripts/afina_selfcheck.py \
    http://172.17.0.1:8001
```

Шаг, на котором вывод обрывается, и есть поломка: 2 — DNS, 3 — сеть или
firewall, 4 — сертификат, 5 с кодом 401 — ключ, 200 — всё в порядке. Пятый шаг
печатает итоговый URL целиком: по нему видно, если в `AFINA_API_BASE_URL`
остался путь и он склеился в двойной.

`AFINA_API_BASE_URL` — корень сервиса CRM (`http://хост:порт`), а не эндпоинт:
путь `/api/public/dashboard/...` клиент дописывает сам. Соседние сервисы
(фиды, ingest) витрины не отдают — нужен именно бэкенд Афины CRM.

### Афина на другом хосте

Если публичный адрес Афины с машины дашборда не открывается, подменять надо не
адрес в настройках, а разрешение имени. Вписать внутренний адрес прямо в
`AFINA_API_BASE_URL` не выйдет по двум причинам сразу: сертификат выписан на
имя, и по IP проверка не пройдёт; а nginx на той стороне разбирает vhost по
заголовку `Host` и без правильного имени отдаёт дефолтный сайт (502).

Поэтому имя остаётся публичным, а в `.env` добавляется запись hosts для
контейнера дашборда:

```bash
AFINA_API_BASE_URL=https://afina-crm.ru
AFINA_CRM_HOST_ENTRY=afina-crm.ru:10.0.0.1
```

Она подставляется в `extra_hosts` сервиса `dashboard` (см. docker-compose.yml).
Применяется пересозданием контейнера — `restart` для этого мало:

```bash
docker compose up -d dashboard
docker compose exec dashboard python scripts/afina_selfcheck.py
```

Второй шаг самопроверки должен показать внутренний адрес, четвёртый — принятый
сертификат, пятый — HTTP 200.

Запись статическая: если Афина переедет, дашборд об этом не узнает и покажет
«Афина недоступна». Адрес Афины стоит помнить в том же месте, где помнят про
остальные переезды.
